LACED - COMPLETE DEPLOYMENT RUNBOOK
====================================

This guide matches the current codebase.

Architecture:

    client/       React 19 + Vite frontend
    Laced.Api/    ASP.NET Core .NET 10 backend
    PostgreSQL    Local PostgreSQL or hosted Neon PostgreSQL

Recommended hosted architecture:

    Vercel          React frontend
    Render or       ASP.NET backend
    SmarterASP
    Neon            PostgreSQL database

The backend and frontend have separate URLs. The backend must have a public
HTTPS URL for eSewa callbacks. eSewa cannot call localhost.


1. WHAT THE CODE ACTUALLY USES
==============================

1.1 Backend .env: not used
--------------------------

There is no `Laced.Api/.env` file and the backend does not use dotenv.
ASP.NET Core configuration comes from:

1. `Laced.Api/appsettings.json`
2. `Laced.Api/appsettings.{Environment}.json`
3. Environment variables
4. Command-line arguments

The local HTTPS launch profile in
`Laced.Api/Properties/launchSettings.json` sets:

    ASPNETCORE_ENVIRONMENT=Development

Therefore a normal local run loads:

    Laced.Api/appsettings.json
    Laced.Api/appsettings.Development.json

The root `.gitignore` ignores `Laced.Api/appsettings.Local.json`. You may
create that file for local-only values, but it is loaded only when the
environment is `Local`:

    $env:ASPNETCORE_ENVIRONMENT="Local"

For hosting, do not upload secret configuration files. Set values in Render
or SmarterASP's private application settings.

1.2 Frontend .env: used by Vite
-------------------------------

The frontend reads Vite variables in:

    client/src/services/api.js
    client/vite.config.js
    client/src/utils/image.js

Local files:

    client/.env
    client/.env.example

`.env` and `.env.*` are ignored by Git except `.env.example`.
Vite embeds values when `npm run build` runs. Every production variable
change requires a new frontend build and deployment.

1.3 Exact backend configuration keys
-------------------------------------

ASP.NET nested keys use double underscores in environment variables:

    ConnectionStrings__DefaultConnection
    Jwt__Key
    Jwt__Issuer
    Jwt__Audience
    AdminSeed__Name
    AdminSeed__Email
    AdminSeed__Password
    Esewa__PaymentUrl
    Esewa__StatusCheckUrl
    Esewa__ProductCode
    Esewa__SecretKey
    Esewa__SuccessPath
    Esewa__FailurePath
    Backend__BaseUrl
    Frontend__BaseUrl
    Frontend__SuccessPath
    Frontend__FailurePath

These values are defined/consumed by:

    Laced.Api/appsettings.json
    Laced.Api/appsettings.Development.json
    Laced.Api/Program.cs
    Laced.Api/Features/Payments/EsewaService.cs
    Laced.Api/Features/Payments/PaymentController.cs

`appsettings.json` is an empty production-shaped template. The backend needs
real values from the host or it will fail during startup.

1.4 PostgreSQL and migrations
-----------------------------

The backend uses PostgreSQL through Npgsql. Important files:

    Laced.Api/Data/ApplicationDbContext.cs
    Laced.Api/Laced.Api.csproj
    Laced.Api/Program.cs
    Laced.Api/Migrations/

At startup, `Program.cs` runs:

    await dbContext.Database.MigrateAsync();

The configured database user must be able to create and alter tables.
Existing migrations:

    20260924152140_InitialCreate
    20260924154920_ProductsAndCart
    20260925111557_OrdersCheckout
    20260925114020_EsewaPaymentsAndRefunds

Do not create a migration merely because the app moved to another computer or
provider. Create one only after changing an EF model/schema.

1.5 Admin seed behavior
-----------------------

`SeedIdentityAsync` in `Laced.Api/Program.cs` runs at startup. It:

- Creates `User` and `Admin` roles if missing.
- Requires `AdminSeed:Name`, `AdminSeed:Email`, and `AdminSeed:Password`.
- Creates the admin only when that email does not already exist.
- Adds the Admin role to that user if it is missing.

Changing seed values does not reset an existing admin password or rename an
existing admin. After a role change, log out and log in again so the new JWT
contains current role claims.

1.6 CORS behavior
-----------------

`Program.cs` configures exactly one CORS origin from `Frontend:BaseUrl`.
It must exactly match the browser frontend origin, including `https://`, with
no trailing slash:

    Correct:   https://laced.vercel.app
    Incorrect: https://laced.vercel.app/

1.7 eSewa behavior
------------------

`EsewaService.cs` builds callback URLs as:

    Backend:BaseUrl + Esewa:SuccessPath
    Backend:BaseUrl + Esewa:FailurePath

Use these paths:

    /api/payments/esewa/success
    /api/payments/esewa/failure

The resulting URLs must be public HTTPS URLs. `PaymentController.cs` accepts
anonymous GET/POST callbacks and redirects to:

    Frontend:BaseUrl/Frontend:SuccessPath
    Frontend:BaseUrl/Frontend:FailurePath

Use these frontend paths:

    payment/success
    payment/failure

Use a complete matching eSewa sandbox set or a complete production set. Do not
mix sandbox URLs with production credentials.

1.8 Product image storage
-------------------------

`ProductService.cs` uploads files to the configured Cloudinary folder. The
database stores Cloudinary HTTPS URLs, which the frontend uses directly.
Image delivery therefore does not depend on the API container filesystem or
Render instance lifecycle.


2. VALUES TO PREPARE
====================

2.1 Local PostgreSQL
--------------------

    Host=localhost;Port=5432;Database=laced;Username=postgres;Password=YOUR_PASSWORD

2.2 Neon PostgreSQL
-------------------

Copy the exact connection string from Neon. It commonly looks like:

    Host=ep-example.region.aws.neon.tech;Port=5432;Database=neondb;Username=USER;Password=PASSWORD;SSL Mode=Require

Do not put this value in frontend code or any `VITE_*` variable.

2.3 Security
------------

Generate a new long JWT key for every hosted environment. Do not use the
current development key from `appsettings.Development.json` in production.
Prepare a separate strong admin password.

2.4 eSewa
---------

Prepare the matching:

    Payment URL
    Status-check URL
    Product code
    Secret key

The development file contains test-style eSewa values. Rotate credentials if
they have been exposed publicly.

2.5 Final URLs
--------------

You need these before configuring CORS and payment callbacks:

    FRONTEND_URL=https://YOUR-VERCEL-DOMAIN
    BACKEND_URL=https://YOUR-RENDER-OR-SMARTERASP-DOMAIN

Never use localhost in hosted values. Never add a trailing slash.


3. RUN ON ANOTHER WINDOWS DEVICE
================================

This local arrangement is:

    Frontend: http://localhost:5173
    Backend:  https://localhost:7183
    Database: local PostgreSQL

It is suitable for development. It cannot receive public eSewa callbacks.

3.1 Install software
--------------------

Install:

- Git: https://git-scm.com/downloads
- .NET 10 SDK: https://dotnet.microsoft.com/download/dotnet/10.0
- Node.js LTS: https://nodejs.org/
- PostgreSQL 16 or newer: https://www.postgresql.org/download/windows/

Verify:

    git --version
    dotnet --version
    node --version
    npm --version
    psql --version

3.2 Clone
---------

    git clone YOUR_GITHUB_REPOSITORY_URL
    cd Laced

3.3 Create the database
-----------------------

Create a PostgreSQL database named `laced` using pgAdmin or SQL. The user must
have permission to create schema objects.

3.4 Configure the backend
-------------------------

Edit local values in:

    Laced.Api/appsettings.Development.json

Replace the current local password, JWT key, admin password, and eSewa test
values. Required local values are:

    ConnectionStrings:DefaultConnection = local PostgreSQL string
    Jwt:Key                         = local long random key
    Jwt:Issuer                      = Laced.Api
    Jwt:Audience                    = Laced.Client
    AdminSeed:Name                  = local admin name
    AdminSeed:Email                 = local admin email
    AdminSeed:Password              = local admin password
    Esewa:PaymentUrl                = matching test URL
    Esewa:StatusCheckUrl            = matching test URL
    Esewa:ProductCode               = matching test code
    Esewa:SecretKey                 = matching test secret
    Esewa:SuccessPath               = /api/payments/esewa/success
    Esewa:FailurePath               = /api/payments/esewa/failure
    Backend:BaseUrl                 = https://localhost:7183
    Frontend:BaseUrl                = http://localhost:5173
    Frontend:SuccessPath            = payment/success
    Frontend:FailurePath            = payment/failure

Alternative local-only file:

    Laced.Api/appsettings.Local.json

Set its environment explicitly before running:

    $env:ASPNETCORE_ENVIRONMENT="Local"

Alternative PowerShell variables for one terminal session:

    $env:ConnectionStrings__DefaultConnection="Host=localhost;Port=5432;Database=laced;Username=postgres;Password=YOUR_PASSWORD"
    $env:Jwt__Key="LOCAL_LONG_RANDOM_KEY"
    $env:Jwt__Issuer="Laced.Api"
    $env:Jwt__Audience="Laced.Client"
    $env:AdminSeed__Name="Local Admin"
    $env:AdminSeed__Email="admin@example.com"
    $env:AdminSeed__Password="LOCAL_ADMIN_PASSWORD"
    $env:Backend__BaseUrl="https://localhost:7183"
    $env:Frontend__BaseUrl="http://localhost:5173"

3.5 Restore and migrate
-----------------------

    dotnet restore .\Laced.Api\Laced.Api.csproj
    dotnet tool install --global dotnet-ef
    dotnet ef database update --project .\Laced.Api\Laced.Api.csproj

If EF is already installed:

    dotnet tool update --global dotnet-ef

3.6 Run backend
---------------

    dotnet run --project .\Laced.Api\Laced.Api.csproj --launch-profile https

Open:

    https://localhost:7183/swagger

If the certificate is not trusted:

    dotnet dev-certs https --clean
    dotnet dev-certs https --trust

Startup also migrates the database and seeds roles/admin. The first startup
error is normally the useful one: check database access, required JWT values,
admin seed values, and migration permissions.

3.7 Configure and run frontend
------------------------------

Edit `client/.env`:

    VITE_API_BASE_URL=
    VITE_FRONTEND_PORT=5173
    VITE_BACKEND_URL=https://localhost:7183

The empty API base is correct locally. `client/vite.config.js` proxies `/api`
and `/uploads` to `VITE_BACKEND_URL`.

Install and run:

    npm --prefix .\client install
    npm --prefix .\client run dev

Open:

    http://localhost:5173

Use separate terminals for backend and frontend.

3.8 Test locally
----------------

Test signup, login, product browsing, cart, order creation, admin login,
product creation, and image upload. A local computer cannot receive eSewa's
internet callback. Use a hosted backend for real callback testing.

Optional production-style frontend check:

    npm --prefix .\client run build
    npm --prefix .\client run preview


4. CREATE AND PREPARE NEON
===========================

Do this before either hosted backend option:

1. Create a Neon project/database.
2. Copy its PostgreSQL connection string.
3. Keep the string private.
4. Confirm SSL is included as required by Neon.
5. Give the database user schema creation/alter permissions.

Do not create tables manually. The committed EF migrations create the schema,
and startup also calls `MigrateAsync()`.


5. DEPLOY THE FRONTEND TO VERCEL
================================

This same Vercel setup is used with either SmarterASP or Render.

1. Import the Git repository in Vercel.
2. Set Root Directory to `client`.
3. Set Build command to `npm run build`.
4. Set Output directory to `dist`.
5. Add a Production environment variable:

       VITE_API_BASE_URL=https://YOUR-BACKEND-DOMAIN

6. Deploy and record the Vercel URL.

Do not leave `VITE_API_BASE_URL` empty in production. Do not include `/api`
at the end because frontend endpoints already begin with `/api`.

5.1 Vercel SPA fallback
-----------------------

For browser refreshes of `/shop`, `/products/id`, `/account/orders/id`, and
`/admin`, add this file if required:

    client/vercel.json

    {
      "rewrites": [
        {
          "source": "/(.*)",
          "destination": "/index.html"
        }
      ]
    }

Commit and redeploy it. Without the rewrite, internal navigation may work
while direct route refreshes return 404.

5.2 Vercel after changing backend URL
--------------------------------------

1. Change `VITE_API_BASE_URL` in Vercel Project Settings.
2. Redeploy.
3. Check browser Network requests for the new backend URL.

6.8 IIS route fallback
----------------------

If SmarterASP IIS URL Rewrite is enabled, put this `web.config` beside the
frontend `index.html` in the deployed static site:

    <?xml version="1.0" encoding="utf-8"?>
    <configuration>
      <system.webServer>
        <rewrite>
          <rules>
            <rule name="React Routes" stopProcessing="true">
              <match url=".*" />
              <conditions logicalGrouping="MatchAll">
                <add input="{REQUEST_FILENAME}" matchType="IsFile" negate="true" />
                <add input="{REQUEST_FILENAME}" matchType="IsDirectory" negate="true" />
              </conditions>
              <action type="Rewrite" url="/" />
            </rule>
          </rules>
        </rewrite>
      </system.webServer>
    </configuration>

7.1 Add the Dockerfile
----------------------

Create `Dockerfile` at repository root, beside `client` and `Laced.Api`:

    FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
    WORKDIR /src
    COPY Laced.Api/Laced.Api.csproj Laced.Api/
    RUN dotnet restore Laced.Api/Laced.Api.csproj
    COPY Laced.Api/ Laced.Api/
    RUN dotnet publish Laced.Api/Laced.Api.csproj -c Release -o /app/publish --no-restore

    FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
    WORKDIR /app
    COPY --from=build /app/publish .
    ENTRYPOINT ["sh", "-c", "dotnet Laced.Api.dll --urls http://0.0.0.0:${PORT:-8080}"]

2. In Render select New, Web Service.

4. Choose Docker deployment.

The process must bind to `0.0.0.0` and Render's `PORT`; the Dockerfile does

7.6 Render HTTPS forwarding
---------------------------

The current `Program.cs` calls `app.UseHttpsRedirection()` but does not
configure forwarded headers. Render terminates public HTTPS and may forward
HTTP internally. If the deployed service has an HTTPS redirect loop, update
`Laced.Api/Program.cs`.

Add:

    using Microsoft.AspNetCore.HttpOverrides;

Before `builder.Build()` register:

    builder.Services.Configure<ForwardedHeadersOptions>(options =>
    {
        options.ForwardedHeaders =
            ForwardedHeaders.XForwardedFor |
            ForwardedHeaders.XForwardedProto;
    });

Before `app.UseHttpsRedirection()` add:

    app.UseForwardedHeaders();
    app.UseHttpsRedirection();

Rebuild and redeploy. This change is specifically for a demonstrated proxy
redirect problem; it is not required for normal local development.

7.8 Render limitations
----------------------

Free Render services may sleep. The first request can be slow and the hosted
`EsewaExpirationService` may be delayed. Free/ephemeral storage can delete
product images. Use a persistent disk/object storage and non-sleeping service
for durable production operation.

9. FINAL END-TO-END TEST
========================

Before push:

    dotnet build .\Laced.Api\Laced.Api.csproj
    npm --prefix .\client install
    npm --prefix .\client run lint
    npm --prefix .\client run build

After backend deployment:

1. Open public Swagger.
2. Confirm Neon schema/migrations completed.
3. Confirm seeded admin login.
4. Register a normal user.
5. Browse products.
6. Test cart and order creation.
7. Test admin product creation.
8. Upload and view a product image.

After Vercel deployment:

1. Confirm `VITE_API_BASE_URL` is the public backend origin.
2. Confirm the frontend was redeployed after setting it.
3. Refresh `/shop` directly.
4. Confirm browser API requests are successful.
5. Confirm no CORS error occurs.
6. Confirm images load from the backend domain.

Payment test:

1. Use matching eSewa sandbox or matching production settings.
2. Confirm backend success callback:

       BACKEND_URL/api/payments/esewa/success

3. Confirm backend failure callback:

       BACKEND_URL/api/payments/esewa/failure

4. Confirm success redirect:

       FRONTEND_URL/payment/success

5. Confirm failure redirect:

       FRONTEND_URL/payment/failure

Common problems:

- Frontend network error: wrong `VITE_API_BASE_URL` or Vercel not rebuilt.
- CORS error: `Frontend__BaseUrl` does not exactly match Vercel origin.
- Backend startup error: missing JWT/admin/eSewa value, bad Neon connection,
  or insufficient migration permission.
- Admin access error: log out and in again after role seeding.
- Payment error: localhost URL, mixed eSewa environments, wrong callback URL,
  or incorrect backend/frontend base URL.
- Route refresh 404: missing `client/vercel.json` rewrite or IIS rewrite.
- Missing images: host filesystem is ephemeral or upload directory is not
  writable.
