LACED BACKEND API DOCUMENTATION
================================

This document describes the API currently implemented in the Laced ASP.NET Core backend. The source code is the authority for this document. It documents current behavior, including implementation details and known contract quirks.

Local API URLs
--------------
- HTTP: http://localhost:5096
- HTTPS: https://localhost:7183
- Swagger UI: https://localhost:7183/swagger
- OpenAPI document is generated by Swagger at the Swagger UI route.

GLOBAL RESPONSE FORMAT
======================

Normal controller JSON responses use this wrapper:

{
  "success": true,
  "message": "Human-readable message.",
  "data": {}
}

Fields:
- success: boolean. `true` for the controller's success branch and `false` for explicit controller errors.
- message: string. A human-readable success or failure message.
- data: nullable, object, array, or primitive depending on the endpoint. Successful no-data operations use `null`.

Known data variations:
- `null`: signup, password change, cart item removal, cart clear, order cancellation, admin order cancellation.
- object: authentication, individual products, carts, orders, eSewa payment form data, eSewa status, refund requests.
- array: the current user's refund list and admin refund list.
- paginated object: product and order list responses.

Normal explicit failures also use the wrapper:

{
  "success": false,
  "message": "Reason for failure.",
  "data": null
}

Important validation variation:
- Controllers use `[ApiController]`.
- Automatic model-validation failures are generated by ASP.NET Core, not by the custom wrapper. They use the framework's validation problem-details structure, normally similar to:

{
  "type": "...",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": {
    "fieldName": ["The fieldName field is required."]
  },
  "traceId": "..."
}

The exact `type` URL and `traceId` value are runtime/framework-generated and are not determined from the application implementation.

Authentication failures and authorization failures are generated by ASP.NET Core JWT middleware. Their exact response body is not customized by this backend and is therefore not determined from the current implementation.

All normal JSON property names are serialized in camelCase by the ASP.NET Core JSON defaults. Dates are JSON ISO-8601 date/time values. Database DateTime values are UTC timestamps. Decimal values such as prices and totals are JSON numbers.

AUTHENTICATION AND JWT
=====================

Send the JWT on authenticated requests using:

Authorization: Bearer <JWT>

The JWT is obtained from `POST /api/auth/login`. JWT validation checks the configured signing key, issuer, audience, expiration, and lifetime. Tokens are created with a two-hour expiration and zero clock skew.

The token contains claims for:
- subject/user ID
- name identifier/user ID
- name
- email
- role claims

Roles seeded by the backend:
- User
- Admin

A user receives the `User` role during signup. A development admin is seeded from configuration and receives the `Admin` role.

AUTH API
========

1. POST /api/auth/signup
------------------------
Authentication: Anonymous.
Headers:
- `Content-Type: application/json`.
- No Authorization header is required.

Route parameters: none.
Query parameters: none.

Request body:

{
  "name": "John Doe",
  "email": "john@example.com",
  "password": "Password123!"
}

Fields:
- name: string, required, not nullable. No additional application-specific length rule is declared.
- email: string, required, not nullable, must pass `EmailAddress` validation. Identity also requires a usable unique email/user name.
- password: string, required, not nullable, minimum length 6 from the request DTO. Identity password rules also apply.

Success:
- HTTP 200 OK.
- Response message: `Registration successful.`
- `data`: null.

{
  "success": true,
  "message": "Registration successful.",
  "data": null
}

Failure:
- HTTP 400 Bad Request for explicit Identity creation or role-assignment failures.
- The message contains the Identity error descriptions joined into one string.
- Automatic DTO validation errors are framework validation responses as described above.

{
  "success": false,
  "message": "Identity error message.",
  "data": null
}

Business rules:
- The new account gets the User role.
- If role assignment fails, the newly created user is deleted.
- Signup does not return a token.
- Signup does not return a user object.

Example:

POST /api/auth/signup

{
  "name": "John Doe",
  "email": "john@example.com",
  "password": "Password123!"
}

2. POST /api/auth/login
-----------------------
Authentication: Anonymous.
Headers:
- `Content-Type: application/json`.

Request body:

{
  "email": "john@example.com",
  "password": "Password123!"
}

Fields:
- email: string, required, valid email format.
- password: string, required.

Success:
- HTTP 200 OK.
- Message: `Login successful.`
- Data is `AuthResponse`.

{
  "success": true,
  "message": "Login successful.",
  "data": {
    "token": "JWT_TOKEN",
    "user": {
      "id": "00000000-0000-0000-0000-000000000000",
      "name": "John Doe",
      "email": "john@example.com",
      "role": "User"
    }
  }
}

Actual response fields:
- token: string, JWT.
- user: object.
- user.id: GUID serialized as a string.
- user.name: string.
- user.email: string.
- user.role: string, normally `User` or `Admin`.

Important source-code note: the current backend uses the same `UserProfileResponse` inside `AuthResponse` and that DTO currently contains `id`. Therefore the current implementation does return a user ID in login, even though the earlier intended contract said login should not return one. This documentation records the actual current behavior.

Failure:
- HTTP 401 Unauthorized when the email does not exist or the password is invalid.
- Message: `Invalid email or password.`

{
  "success": false,
  "message": "Invalid email or password.",
  "data": null
}

7. POST /api/products
---------------------
Authentication: JWT required.
Role: Admin.
Headers:
- `Authorization: Bearer <ADMIN_JWT>`.
- `Content-Type: multipart/form-data`.

This is a multipart request. Do not send the whole request as JSON. The `sizes` field is one JSON string, and `images` can contain multiple uploaded files.

Form fields:
- name: string, required, not nullable.
- description: string, optional; defaults to empty string.
- brand: string, required, not nullable.
- price: decimal, required value, minimum 0.01.
- isActive: boolean, optional; defaults to true.
- sizes: string containing a JSON array, optional; defaults to `[]`.
- images: one or more `IFormFile` values, optional.
- heroImageFileName: string, optional.
- heroImageId: string/GUID-like value, optional; mostly useful for update.
- heroImageIndex: integer, optional, zero-based index within newly uploaded images.
- removeImageIds: comma-separated image GUIDs, optional; mostly useful for update.

Sizes JSON format:

[{"size":42,"quantity":5},{"size":43,"quantity":2}]

Size validation:
- size must be greater than zero.
- quantity must be zero or greater.
- the same size cannot appear more than once in the JSON array.
- the database also enforces unique ProductId plus Size.

Image validation:
- accepted extensions: `.jpg`, `.jpeg`, `.png`, `.webp`.
- accepted content types: `image/jpeg`, `image/png`, `image/webp`.
- each file must be nonempty.
- maximum file size is 5 MB.
- files are stored in the configured Cloudinary folder.
- public URLs are Cloudinary secure URLs returned by the API.

Hero selection precedence:
1. Matching `heroImageId`.
2. Matching `heroImageFileName`.
3. `heroImageIndex` in the newly uploaded file list.
4. Existing hero image.
5. First available image.

Conceptual request:

POST /api/products
Content-Type: multipart/form-data
Authorization: Bearer ADMIN_JWT

name = Air Max
description = Running sneaker
brand = Nike
price = 12000
isActive = true
sizes = [{"size":42,"quantity":5},{"size":43,"quantity":2}]
heroImageIndex = 0
images = air-max-front.jpg
images = air-max-side.jpg

Success:
- HTTP 200 OK.
- Message: `Product created successfully.`
- Data: ProductResponse.

Failure:
- HTTP 400 Bad Request for product/size/image business validation failures.
- HTTP 401 if no valid JWT.
- HTTP 403 if authenticated without Admin role.
- Automatic multipart/model validation errors use framework validation problem details.

8. PUT /api/products/{id}
-------------------------
Authentication: JWT required.
Role: Admin.
Headers:
- `Authorization: Bearer <ADMIN_JWT>`.
- `Content-Type: multipart/form-data`.

Route parameter:
- id: product GUID.

All update fields are optional. Omitted values preserve the current product values.

Form fields:
- name: nullable/optional string.
- description: nullable/optional string.
- brand: nullable/optional string.
- price: nullable/optional decimal; minimum 0.01 when supplied.
- isActive: nullable/optional boolean.
- sizes: nullable/optional JSON string. When supplied, it replaces the product's size inventory list. When omitted, existing sizes are unchanged.
- images: optional list of `IFormFile` files.
- heroImageFileName: optional string.
- heroImageId: optional existing image GUID.
- heroImageIndex: optional zero-based index among newly uploaded files.
- removeImageIds: optional comma-separated image GUIDs.

Example partial request:

PUT /api/products/product-guid
Content-Type: multipart/form-data
Authorization: Bearer ADMIN_JWT

price = 13500
isActive = true

Example inventory update:

sizes = [{"size":42,"quantity":10},{"size":43,"quantity":4}]

Success:
- HTTP 200 OK.
- Message: `Product updated successfully.`
- Data: ProductResponse.

Failure:
- HTTP 404 Not Found with `Product not found.` when the product does not exist.
- HTTP 400 Bad Request for other validation/business failures.
- HTTP 401/403 from authentication/authorization middleware.

15. POST /api/orders
--------------------
Authentication: JWT required.
Headers:
- `Authorization: Bearer <JWT>`.
- `Content-Type: application/json`.

Request body:

{
  "shippingName": "John Doe",
  "shippingPhone": "9800000000",
  "shippingAddress": "New Baneshwor",
  "shippingCity": "Kathmandu",
  "shippingPostalCode": "44600",
  "paymentMethod": "COD"
}

Fields:
- shippingName: string, required.
- shippingPhone: string, required.
- shippingAddress: string, required.
- shippingCity: string, required.
- shippingPostalCode: nullable/optional string.
- paymentMethod: string, required. Accepted case-insensitive values are `COD` and `Esewa`.

The request does not contain products, sizes, quantities, or prices. Items are read from the current cart.

Business rules:
- cart must exist and contain items.
- every product must still be active.
- every cart size/product relationship is checked.
- requested quantity must be available.
- current product prices are read from the database.
- OrderItems store product name, size, unit price, quantity, and line total snapshots.
- inventory is reduced and cart items are cleared in one transaction.
- COD starts with PaymentStatus Pending and OrderStatus Confirmed.
- eSewa starts with PaymentStatus Pending and OrderStatus Pending.

Success:
- HTTP 200 OK.
- Message: `Order placed successfully.`
- Data: OrderResponse.

Failure:
- HTTP 400 Bad Request for invalid payment method, empty cart, inactive product, invalid size relationship, or insufficient inventory.

18. POST /api/orders/{id}/cancel
--------------------------------
Authentication: JWT required.
Headers:
- `Authorization: Bearer <JWT>`.

Route parameter:
- id: order GUID.
Request body: none.

Cancellable states:
- Pending
- Confirmed
- Processing

Non-cancellable states:
- Shipped
- Delivered
- Cancelled

Success:
- HTTP 200 OK.
- Message: `Order cancelled successfully.`
- data: null.
- Purchased inventory is restored in a transaction.
- A previously Cancelled order is not restored twice.
- For COD, payment status remains Pending.

Failure:
- HTTP 400 Bad Request for a missing order, already-cancelled order, shipped/delivered order, or missing purchased size.

- Data: OrderResponse.

Failure:
- HTTP 400 Bad Request for invalid status, missing order, or invalid transition.

23. POST /api/payments/esewa/initiate/{orderId}
------------------------------------------------
Authentication: JWT required.
Headers:
- `Authorization: Bearer <JWT>`.

Route parameter:
- orderId: GUID.
Request body: none.

Rules:
- order must belong to the current user.
- PaymentMethod must be `Esewa`.
- PaymentStatus cannot already be `Paid`.
- order cannot be `Cancelled`.
- order must be less than 30 minutes old.

Success:
- HTTP 200 OK.
- Message: `eSewa payment initiated.`
- Data:

{
  "paymentUrl": "https://rc-epay.esewa.com.np/api/epay/main/v2/form",
  "fields": {
    "amount": "1000.00",
    "tax_amount": "0",
    "total_amount": "1000.00",
    "transaction_uuid": "orderguid-20260925120000000",
    "product_code": "EPAYTEST",
    "product_service_charge": "0",
    "product_delivery_charge": "0",
    "success_url": "configured-success-url",
    "failure_url": "configured-failure-url",
    "signed_field_names": "total_amount,transaction_uuid,product_code",
    "signature": "BASE64_HMAC_SIGNATURE"
  }
}

Field details:
- paymentUrl: string. Frontend submits the form directly to this URL.
- amount: string decimal formatted with two decimal places. Send to eSewa.
- tax_amount: string, always `0`. Send to eSewa.
- total_amount: string decimal formatted with two decimal places. Send to eSewa and is signed.
- transaction_uuid: string containing the order GUID without separators plus a timestamp. Send to eSewa and is signed.
- product_code: string, configured as `EPAYTEST`. Send to eSewa and is signed.
- product_service_charge: string, always `0`. Send to eSewa.
- product_delivery_charge: string, always `0`. Send to eSewa.
- success_url: string. eSewa callback URL.
- failure_url: string. eSewa failure callback URL.
- signed_field_names: string, exactly `total_amount,transaction_uuid,product_code`.
- signature: Base64 HMAC-SHA256 signature. Send to eSewa; the frontend does not calculate it.

Frontend behavior:
1. Call this Laced endpoint with the order ID.
2. Read `paymentUrl` and every entry in `fields`.
3. Create an HTML POST form with those fields.
4. Submit that form directly to eSewa's `paymentUrl`.
5. Do not send the form fields to another Laced API endpoint.

Failure:
- HTTP 400 Bad Request for incomplete configuration, missing order, wrong payment method, already-paid order, cancelled order, or expired order.

25. POST /api/payments/esewa/status/{orderId}
---------------------------------------------
Authentication: JWT required.
Headers:
- `Authorization: Bearer <JWT>`.

Route parameter:
- orderId: GUID.
Request body: none.

The backend calls the configured eSewa status URL with:
- product_code
- total_amount
- transaction_uuid

Success:
- HTTP 200 OK.
- Message: `eSewa status checked successfully.`
- Data: EsewaStatusResponse.

{
  "success": true,
  "message": "eSewa status checked successfully.",
  "data": {
    "productCode": "EPAYTEST",
    "transactionUuid": "transaction-uuid",
    "totalAmount": 1000.00,
    "status": "COMPLETE",
    "refId": "reference-id"
  }
}

Status mapping:
- COMPLETE: PaymentStatus becomes Paid and OrderStatus becomes Confirmed.
- PENDING: no paid transition.
- FULL_REFUND: PaymentStatus becomes Refunded.
- CANCELED: PaymentStatus becomes Failed.
- NOT_FOUND and AMBIGUOUS: current service leaves the local status unchanged.

Before marking paid, product code, transaction UUID, and total amount must match the order.

Failure:
- HTTP 400 Bad Request for missing order, wrong user, non-eSewa order, missing transaction UUID, incomplete configuration, remote error, or mismatch.

26. GET/POST /api/payments/esewa/success
----------------------------------------
Authentication: Anonymous.
This is intended for the eSewa/browser callback, not normal authenticated API use.

Input:
- Query string `data`: Base64/Base64URL-encoded eSewa JSON response.
- For a form POST, the endpoint also reads form field `data` if the query value is empty.

Decoded data fields expected by the DTO:
- transaction_code: string.
- status: string.
- total_amount: decimal.
- transaction_uuid: string.
- product_code: string.
- signed_field_names: comma-separated string.
- signature: Base64 string.

Example conceptual callback:

GET /api/payments/esewa/success?data=BASE64_ENCODED_JSON

Processing rules:
- Base64 data is decoded.
- JSON is deserialized.
- signature is verified using the configured secret.
- transaction UUID must match an existing order.
- product code must match configuration.
- total amount must match the order.
- COMPLETE changes PaymentStatus from Pending to Paid and OrderStatus to Confirmed.
- repeated successful callbacks do not process payment twice.

Response:
- HTTP redirect, not the global JSON wrapper.
- Successful verified payment redirects to:
  `{Frontend:BaseUrl}/payment-success?orderId={id}&status=success`
- A valid callback with a non-COMPLETE status redirects to `status=pending`.
- Invalid/missing data or failed verification redirects to:
  `{Frontend:BaseUrl}/payment-failure?status=invalid`

27. GET/POST /api/payments/esewa/failure
----------------------------------------
Authentication: Anonymous.
Intended for the eSewa/browser callback.

Request body/query: no application fields are required by this action.

Response:
- HTTP redirect to:
  `{Frontend:BaseUrl}/payment-failure?status=failed`
- This action does not directly mark the order paid.
- It does not immediately restore inventory.
- Pending order cleanup is handled by the periodic expiration service.

ENUMS
=====

Enum: PaymentMethod
Values:
- COD: numeric value 0.
- Esewa: numeric value 1.
Used by order creation and eSewa/refund business rules. Order request accepts the string names, case-insensitively. Responses serialize enum values as numbers by the current JSON configuration.

Enum: PaymentStatus
Values:
- Pending: numeric value 0.
- Paid: numeric value 1.
- Failed: numeric value 2.
- Refunded: numeric value 3.
Used on Order and in order filters, eSewa processing, and refund eligibility.

Enum: OrderStatus
Values:
- Pending: numeric value 0.
- Confirmed: numeric value 1.
- Processing: numeric value 2.
- Shipped: numeric value 3.
- Delivered: numeric value 4.
- Cancelled: numeric value 5.
Used on Order, order filters, user/admin cancellation, and admin status updates.

Enum: RefundStatus
Values:
- Requested: numeric value 0.
- Approved: numeric value 1.
- Rejected: numeric value 2.
- Paid: numeric value 3.
Used on RefundRequest and admin refund status updates.

CONFIGURATION AND RUNTIME BEHAVIOR
==================================

Current Development configuration contains:
- PostgreSQL connection string under `ConnectionStrings:DefaultConnection`.
- JWT configuration under `Jwt:Key`, `Jwt:Issuer`, and `Jwt:Audience`.
- Development admin seed under `AdminSeed:Name`, `AdminSeed:Email`, and `AdminSeed:Password`.

Static files are enabled. Uploaded product images can be requested using the returned relative URL:

https://res.cloudinary.com/<cloud-name>/image/upload/<public-id>

Swagger has a Bearer security definition and an Authorize button. Enter the JWT according to the Swagger UI's bearer prompt.

No CORS policy is configured in the current backend. Cross-origin frontend behavior is therefore not configured by this API.

FRONTEND INTEGRATION NOTES
==========================

- Local HTTP base URL: `http://localhost:5096`.
- Local HTTPS base URL: `https://localhost:7183`.
- Swagger URL: `https://localhost:7183/swagger`.
- Use `Authorization: Bearer <JWT>` for every authenticated endpoint.
- Use the Admin JWT for Admin endpoints.
- Signup does not return a token.
- The actual current login response includes `data.user.id` because the shared profile DTO includes ID. The intended earlier contract saying login should not include an ID is not reflected by the current source.
- `/api/auth/me` includes the user ID.
- Product creation/update uses multipart/form-data. The sizes field is a JSON string, not repeated scalar fields.
- Product images are uploaded as repeated `images` file fields.
- Product image URLs are absolute Cloudinary HTTPS URLs and are served independently of the API container.
- Product list pagination is in `data.items`, `data.page`, `data.pageSize`, `data.totalItems`, and `data.totalPages`.
- Public product reads only show active products.
- Cart totals use current product prices; carts do not reserve inventory.
- Order placement reads items and prices from the current cart/database. The frontend cannot submit arbitrary order prices.
- Order item name, size, price, quantity, and line total are stored snapshots.
- Order and refund enum values are emitted as numeric JSON values by the current serializer unless the client converts them using the enum tables above.
- eSewa initiation returns a URL and fields. The frontend must POST those fields directly to eSewa in an HTML form.
- eSewa success/failure routes redirect to `Frontend:BaseUrl`; they do not return the normal JSON response wrapper.
- eSewa callback data is Base64/Base64URL-encoded and is verified by the backend.
- Pending eSewa orders are checked by a hosted service every five minutes and expire after 30 minutes based on CreatedAt.
- A failure callback alone does not restore inventory; expiration/cancellation behavior does that.
- Refunds are manual. The Admin status `Paid` records that a manual refund was completed; no automatic bank/eSewa refund is performed.
- Date fields use ISO-8601 UTC values.
- Money and sizes are decimal JSON numbers. eSewa form money fields are strings formatted to two decimal places.
- Automatic validation errors and authentication/authorization failures use framework-generated responses rather than the custom ApiResponse wrapper.
- No additional endpoints, health endpoint, CORS endpoint, or file-delete endpoint is currently implemented.
